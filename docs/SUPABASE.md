# قاعدة بيانات Supabase

## الإعداد

- من مشروع Supabase المقصود افتح **Connect** واختر PostgreSQL **Session pooler** (عادة المنفذ 5432، يدعم IPv4). استخدم الرابط كما توفره اللوحة، مع استبدال كلمة المرور وترميز محارفها الخاصة URL-encoding. الاتصال المباشر متاح إذا كانت الاستضافة تدعم IPv6.
- احفظه في `SUPABASE_DB_URL` على الخادم فقط. لا ترسله في المحادثة ولا تضفه إلى `VITE_*`. مفاتيح Supabase API لا تحل محل رابط PostgreSQL.
- الاتصال يستخدم TLS مع التحقق من الشهادة. عند الحاجة أضف شهادة CA الموثوقة من إعدادات Supabase إلى `SUPABASE_DB_CA`. لا تعطل التحقق لإخفاء خطأ شهادة.
- نفذ `npm run db:migrate` ثم `npm start`. لا توجد قاعدة SQLite احتياطية صامتة عند فشل الاتصال.
- المشروع المعتمد: **rddly** (`jbzgpfcvtqjspvuuhogx`)، منطقة `eu-central-1`. جرى استئناف المشروع وإنشاء مخطط `eldevo` وجداوله، وفحص صلاحياتها في 2026-09-19. بقي ضبط `SUPABASE_DB_URL` في الاستضافة؛ لم يتم ربط خادم الموقع الحي بعد.
- طُبق الترحيل الأول عبر إدارة Supabase مع تسجيل اسمه وchecksum نفسه في `eldevo.migrations` داخل العملية نفسها. لذلك يتعرف عليه `npm run db:migrate` كترحيل مطبق، ولا يعيد إنشاء الجداول. استخدم الأمر لترحيلات التطبيق التالية.

## المعمارية والصلاحيات

كل جداول التطبيق في مخطط خاص `eldevo`: users، sessions، records، ledger، audit، resets، limits. لا تضف المخطط إلى exposed schemas في Data API. تفعيل RLS وسحب امتيازات PUBLIC وanon وauthenticated يمنع الوصول العام؛ الخادم يتصل بمالك جداول التطبيق. جميع قرارات الدور والملكية ما زالت في API الخادم. لا تطلب مفاتيح جوجل ولا بيانات دخول Play Console.

المستخدمون يستمرون باستخدام تسجيل الدخول الحالي، وتُحفظ hashes كلمات المرور والجلسات في Supabase PostgreSQL. هذا التعديل لا يحول التسجيل إلى Supabase Auth، ولا يغير تكامل Whop.

كل عملية مالية تتم داخل معاملة واحدة باستخدام الاتصال نفسه وAsyncLocalStorage. قفل `pg_advisory_xact_lock` مشترك بين نسخ الخادم يسلسل تعديل السجلات والمحافظ، ومفاتيح الحركة الفريدة تمنع تكرار الائتمان. الاتصالات خارج المعاملة تستعمل معاملة قصيرة. الانتظار محدود، والفشل يعيد المعاملة كاملة. القفل العام مناسب لحجم إطلاق أولي؛ زيادة الحمل تتطلب تحويله إلى أقفال لكل محفظة/طلب مع اختبارات تنافس، بدل حذفه.

التحقق الخارجي من Google Play وإنشاء جلسة Whop يحدثان خارج المعاملات طويلة القفل. النتائج تحفظ بعد إعادة قراءة الحالة. يبقى مسح الملفات بشريًا، والسحب الرقمي يدوي التنفيذ.

## ترحيل بيانات SQLite الموجودة

1. أوقف الموقع القديم عن الكتابة، وخذ نسخة كاملة من قاعدة SQLite ومجلد uploads. احتفظ بالأصل لاستعادة الخدمة عند الحاجة.
2. جهز قاعدة Supabase فارغة للتطبيق وشغّل `npm run db:migrate`.
3. عيّن `SQLITE_IMPORT_PATH` إلى مسار ملف `eldevo.sqlite` القديم، ثم شغّل `npm run db:import-sqlite`.
4. الأداة تفتح المصدر للقراءة فقط، وترفض أي جداول هدف غير فارغة. تستورد المستخدمين وكلمات المرور المشفرة والجلسات والسجلات والحركات وسجل التدقيق والرموز والحدود داخل معاملة واحدة، ثم تطابق أعداد الصفوف وتتحقق من عدم سلبية الأرصدة. الفشل يتراجع عن كل الكتابات. إعادة تنفيذها بعد النجاح ترفض الاستيراد بدل مضاعفة البيانات.
5. أبقِ ملفات `uploads` في `DATA_DIR` بنفس أسماء معرفاتها. تحقق من الدخول وتنزيل ملف خاص والأرصدة قبل فتح الموقع للكتابة من جديد. لا تشغّل النسختين ككتّاب أثناء النقل.

## الاستضافة والاختبارات

نقل القاعدة لا يحوّل المشروع إلى موقع ثابت أو Vercel Serverless: يحتاج خدمة Node مستمرة للـ API والتحقق الدوري، وتخزينًا دائمًا لرفع الملفات. نقل الملفات إلى Supabase Storage سيكون تعديلًا منفصلًا.

`npm test` يستخدم PostgreSQL مضمّنًا عبر PGlite، مع نفس مخطط SQL ومعاملات القاعدة؛ لا يتصل ببيانات حقيقية. PGlite ممنوع خارج بيئة الاختبار. CI يضيف PostgreSQL 17 فعليًا لاختبار اتصال pg وتكرار الترحيل والتزامن والصلاحيات. `npm run test:browser` يختبر واجهة الموقع من طرف إلى طرف مع قاعدة اختبار مستقلة.

الترحيلات في `supabase/migrations`، وسجل الترحيل التشغيلي في `eldevo.migrations` مع checksum. استخدم `npm run db:migrate` كمسار تطبيق واحد؛ لا تخلطه مع `supabase db push` على نفس القاعدة. ملفات SQL لا تنشئ سياسات تمنح المتصفح حق تعديل الأرصدة.

المراجع: [اتصال PostgreSQL في Supabase](https://supabase.com/docs/guides/database/connecting-to-postgres)، [معاملات node-postgres](https://node-postgres.com/features/transactions).
